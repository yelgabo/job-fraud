Job-fraud agentic flow

How a WorkBC job posting becomes a published Low, Medium or High rating. This report covers which steps are plain code, which are single model calls and which are agents, and the rules that stop any model or agent from publishing a claim on its own.

The short version

job-fraud collects WorkBC postings and rates each one on whether it looks like a genuine attempt to hire locally, as opposed to an advert placed to show that no Canadian applied. The rating is published next to a real employer's name, and the whole design follows from that. Models and agents gather evidence. Code turns the evidence into the number.

There are three phases, and they share one Postgres database without calling each other. A scraper collects postings and marks them pending. A judge evaluates pending postings. A read-only Next.js site shows the judged ones. The judge has two front ends. The API judge is one Node process that calls Claude through the Anthropic API. The keyless judge is a Claude Code session that sends helper agents to research employers on the web. Both hand their evidence to the same composer, so the same evidence gets the same score whichever path gathered it. The evidence itself can differ. The API judge's verifier sees an 800-character description excerpt where keyless helpers see 1,800, and the API path records verbatim search blocks where keyless helpers report their own searches.

  • Agents are given no database step. During a run, one process writes: the API judge itself (from several concurrent tasks inside it), or judge-keyless:apply on the keyless path.
  • Agents never choose a score. If a helper returns a score, signals or reasoning, the apply step drops them before it reads the verdict.
  • Each employer is researched once per run, however many postings it has. A run over 4,243 postings web-checked 219 employers.
  • The cheap model goes first. Haiku 5.5 checks every employer that needs a web check, and Opus 5.5 re-checks any verdict that would raise a rating, plus two cases that would lower it or leave it unclear.
  • An out-of-credit error stops the run and leaves postings pending, so an empty wallet cannot publish a wave of blank ratings.

The system in one picture

The scraper is deterministic. It reads WorkBC's JSON search and detail APIs, runs regex checks over each description (free email domain, mail-in résumé, crypto payment, banking details or ID before an offer, a fee to apply, WhatsApp or Telegram only), buckets the NOC occupation code into a job category, and classifies the apply link's host against a registry of applicant tracking systems such as Workday and Greenhouse. New postings arrive with scoredAt null, and null is what pending means everywhere else in the system. Re-scraping a posting that is already judged updates its fields and leaves it judged.

The site only shows judged rows. Public pages are cached for 600 seconds, so a judge run is visible within ten minutes, or immediately when REVALIDATE_TOKEN is set and the run can call POST /api/revalidate. There is no staging database. A local judge run writes to production and is live once the cache turns over. The site's only write path is the token-gated /audit mirror, where the owner can leave a note or ask for a posting to be judged again.

Two judge paths, one scorer

One predicate picks the path: is ANTHROPIC_API_KEY non-empty in .env? If it is, npm run judge does everything in one process. If it is not, the keyless judge runs inside a Claude Code session and uses that session's agents for web research. A second predicate, TYPESAFE_API_KEY, decides whether Jev answers the text questions. Without it the regex flags stand in for Jev's route judgment and the row stores judgments = null.

What the two share matters more than what differs. Both decide each employer with verificationAction, both enforce the same escalation rule, and both score through buildVerdict in lib/scoring/verdict.ts. The grouping differs in one detail. The keyless fetch groups through planByEmployer, which sends a posting with no employer to the web check on its own, while judge.ts groups inline and gives such a posting no employer check at all.

A failed employer check holds its postings back. When a check fails for any reason other than billing (a refusal, a malformed answer after the retry, a failed Opus re-check), judge.ts logs it and stage 2 skips that employer's postings, which stay pending. Until 6 November 2026 stage 2 scored them anyway on whatever verdict was cached. A placeholder key still causes trouble. It counts as set, every Anthropic call returns 401, and while postings that needed a check stay pending, postings whose employer has a cached or presumed verdict are scored without the impersonation check. On a keyless machine, leave the ANTHROPIC_API_KEY line in .env commented out.

The keyless judge, step by step

This is the multi-agent part of the system. One Claude Code session owns the whole run. It runs the fetch CLI, spawns helper agents, writes their output to files, and runs the apply CLI. The repo's update-postings skill wraps it, and judge-postings holds the procedure and the agent prompt. The skill insists that one session own the run rather than handing batches to separate top-level sessions, because a single owner can restart the run and its progress stays visible.

What a helper receives

The fetch step writes one item per employer that needs a web check, 15 employers to a batch file by default. The item carries the employer's representative posting, chosen as the first posting that gives a mailing address when any does (pickRepresentative). The mailing-address type is the heaviest signal the check produces, and the verifier can only judge an address it has been shown.

{
  "workbcId": "49588691",
  "title": "...", "employer": "...", "location": "...", "salary": "...", "postedAt": "...",
  "atsProvider": "workday", "externalApplyOk": null,
  "flags": [{ "flag": "mail_physical_resume", "evidence": "..." }],
  "descriptionExcerpt": "first 1800 characters of the description",
  "employerPostings": ["49588691", "49588702"]
}

employerPostings is for the apply step, which scores every posting in that list with the employer's verdict. The helper does not need it.

What a helper returns

A JSON array with one verdict per item. The verdict describes the employer. It has no score field.

{
  "workbcId": "49588691",
  "web": {
    "websiteUrl": "https://acme.com",
    "websiteReachable": "yes",          // yes | no | unknown
    "businessMatch": "match",           // match | mismatch | uncertain
    "locationMatch": "match",           // match | mismatch | uncertain
    "hasJobsListing": "yes",            // yes | no | unknown
    "applicationAddressType": "business",
    "confidence": 0.85,
    "summary": "at most 400 characters, shown on the site",
    "verifiedBy": "haiku-5.5"           // set by the orchestrator
  }
}

applicationAddressType is one of business, residential, home_business, po_box, virtual, none or uncertain. home_business needs two sources: the company's own website and at least one independent listing must both give the home as the business address, and otherwise the answer is residential.

What a helper may not do

  • Write to the database. Helpers return JSON to the orchestrator and nothing else. This rests on the prompt and the skill; no tool restriction enforces it.
  • Choose a score. The apply step parses verdicts with a zod schema that keeps only workbcId and web.
  • Return a verdict it did not investigate. If a search fails or the session's search budget runs out, the helper leaves that employer out of its array. An uninvestigated uncertain would be cached on the employer and reused by every later run, while a missing verdict only keeps the postings pending.
  • Call an employer a mismatch because its industry differs from the role. A retailer hiring a developer is a match. Mismatch is reserved for fake, shell, parked or impersonating entities.

The gates in the apply step

judge-keyless:apply is the only place a keyless score is computed. For each verdict, in order:

  1. Parse it with VerdictSchema. A partial or malformed web object fails and the employer's postings stay pending.
  2. Check the tier rule with tierViolation. A verdict that needs escalation must be marked opus-5.5 or haiku-5.5>opus-5.5; anything else is rejected. On the API path code escalates, and here this check is what catches a skipped escalation step.
  3. Store web on the employer once, then ask Jev and compose a score for each pending posting in that employer's employerPostings. A Jev error stops that employer's remaining postings, which stay pending, though the employer verdict is already stored.

Postings in cached.json get one more check. The apply step re-decides each of those employers against all of its current pending postings. If a new posting has arrived since the fetch, for example one with a mailing address the cached verdict never saw, that employer now needs a web check and its postings stay pending for the next fetch. The orchestrator runs apply with --dry-run first, which validates everything and reports tier violations without writing, and then loops fetch and apply until fetch reports zero pending.

The tiered employer check

Both paths check employers with Haiku 5.5 first. Opus 5.5 checks again, and its verdict replaces Haiku's, when needsEscalation in lib/ai/verify-employer-web.ts returns true:

Haiku's verdictWhy it gets a second look
businessMatch: mismatchAdds 25 points. In the model evaluation Haiku found nothing on a real Vancouver payments company and called it a mismatch, which scored 85, a High rating on a real employer.
locationMatch: mismatchAdds 12 points.
Address residential, po_box or virtualOn every posting that mails applications, adds 40 points and floors the score at 70, which is High.
Address home_businessThis label lowers a rating compared with residential, so the cheap model may never give it alone.
Address uncertain when the posting gives a mailing addressOn 1,000 postings Haiku left a house address uncertain where Opus found the residence.

The split rests on docs/verifier-model-eval.md. On the 21 hand-labelled postings, Haiku followed by Opus on alarming verdicts agreed with the labels 20 times out of 21, the same as Opus alone, and escalated 2 of the 21. The estimated cost was about $0.003 per posting against about $0.026 for Opus on everything, roughly an eighth. Opus also gets up to 10 searches per check instead of 5, because at 5 searches 39 of the 584 verdicts stored on 27 October said the search had been cut off.

A cached employer verdict is reused unless one of four things is true. The run is a --rejudge (an API-judge flag); the cached verdict was presumed from an own-ATS match and a new posting does not apply through that tenant; the cached address type is none but a pending posting gives a mailing address; or the cached verdict breaks the tier rule because it was written before the tiers existed. When the re-check script ran over the first 73 such pending-side verdicts, Opus overturned 47 of them.

The API judge

The API judge is agentic in a narrower sense than the keyless path. Each employer check is one Messages API request that carries two tools: the server-side web_search tool, capped at 5 uses for Haiku and 10 for Opus, and record_web_verification, a client tool whose input schema is the verdict. The model chooses its own search queries and runs them on Anthropic's side. If the server-side loop pauses with pause_turn, the code resends the turn, at most three times. The answer counts only if it arrives as a record_web_verification call that passes zod. Otherwise the request is retried once and then counted as failed. Every search block, including its encrypted result content, goes into EmployerWebSearchLog so the /audit pages can show what the model consulted.

Stage 1 checks four employers at a time and stage 2 scores eight postings at a time, both through p-limit, and the SDK retries rate-limit and overload errors up to five times. Two failure rules keep partial runs safe. An out-of-credit error, which arrives as a 400 and is never retried, sets a flag that turns every queued task into a no-op, and the run throws after the current stage with the completed rows saved. A Jev failure leaves that one posting pending, because composing it without judgments would store a different kind of row under the same scoringVersion.

The weekly job-fraud-scheduler Railway cron service runs this path. On Mondays at 12:17 UTC it runs both scrape passes and then npm run judge -- --limit $JUDGE_LIMIT (1,000 by default) if the service has an Anthropic key. It reaches Postgres over Railway's private network.

The brand-impersonation check

Before scoring each posting, both judges compare the applicant tracking system tenant in the apply link with the employer the posting names. On the keyless path the fetch writes one impersonation-NNN.json item per employer and tenant pair, an Opus helper agent answers it, and apply writes the answer through the same function the API judge uses. Below, the API judge's version. If a posting says it is from one company but its Workday link belongs to another, Opus 5.5 investigates with web search and classifies the relationship as same, affiliate, impersonation or uncertain. The prompt tells it to choose impersonation only when it is confident the two companies are unrelated, so a subsidiary applying through its parent's hiring system is cleared. Results are cached per employer and tenant pair for the rest of the run.

  • same or affiliate: the posting is scored normally.
  • uncertain: the posting gets an apply_host_mismatch_review flag and is scored normally.
  • impersonation: the posting is re-attributed to the real company and written directly as score 90 (High), with reasoning that starts "Brand impersonation:".

This is the one place the system writes a fixed number without the composer. The write sets scoringVersion to null, and every re-scoring script (backfill-ats, recheck-cached-verdicts, recompose, reverify-mail) skips rows whose reasoning starts with that prefix. Before 6 November the write left scoringVersion unchanged and recompose did not check the prefix, so a re-judged composed row could have lost its 90; neither of the two impersonation rows in the database was affected. Opus runs this check because a smaller model labelled a real construction company's division as an impersonation of its parent group. It moved from Opus 4.8 to Opus 5.5 on 27 October without a side-by-side comparison, and no labelled impersonation cases exist yet. Both October runs logged zero impersonations.

How the score is composed

composeScore in lib/scoring/compose.ts is a pure function: the same inputs always give the same output, with no clock, network or model. It works in this order:

  1. Decide whether the application route is disowned. With Jev judgments, it is disowned when routePlausibleForEmployer is below 0.57. Without them, it is disowned when the posting has a free-email or messaging-app-only flag. A disowned route withholds the brand credits (business match, location match, jobs page, business mailing address, no mailing address) while the penalties on the same fields still apply. Confirming that a national chain exists says nothing about a posting that collects replies at a Gmail address.
  2. Apply address signals only to postings that mail applications. The verdict is stored per employer, and a sibling posting that applies online should not inherit one location's street address.
  3. Add a signal for every condition in the weight table that fires. Each condition compares against an explicit value, so a check that returned null, meaning not checked, never counts against a posting.
  4. Add the one weighted Jev judgment, askBeforeHire, worth up to 25 points and nothing at or below probability 0.5.
  5. Sum from a baseline of 20 and clamp to 0 to 100.
  6. Apply the floors. A residential, P.O. box or mail-forwarding address sets a minimum of 70, and so does askBeforeHire above 0.8.
  7. Map to a band. Under 30 is Low, 30 to 69 is Medium, 70 and up is High.

The published reasoning is generated from the composed result by explain.ts, so the prose can never disagree with the number beside it. Before the composer a model wrote that prose without knowing the final score.

Jev answers five questions per posting and only one of them is weighted. routePlausibleForEmployer drives the route gate. employerIsOrganisation, brokerRouting and brandProminence are stored on the row and not weighted, because a question earns a weight only after npm run measure-questions shows it separates the bands. Brand prominence is the instructive case. It reads about the same on low and medium postings because the medium band is full of big brands, so weighting it directly would penalise size.

Guardrails

These are the properties a reviewer should check are still true after any change to the judge.

  • One writing process. Helpers are given no database step. On the API path every write comes from one process, from up to 4 or 8 concurrent tasks that each update their own rows; keyless apply writes sequentially (scripts/judge.ts, scripts/judge-keyless-apply.ts). The owner's /audit actions can still write during a run.
  • Evidence in, number out. Agents return employer verdicts. Jev returns probabilities. lib/scoring/compose.ts produces every composed score.
  • Escalation is checked in code. The API path escalates in code. The keyless apply step rejects any verdict that needs escalation and lacks an Opus marker (tierViolation), though that marker is a string the orchestrating session sets itself.
  • Unknown stays neutral. uncertain and unknown add nothing, null checks match no weight-table condition, and a helper omits what it could not search.
  • Failures leave work pending. A billing error aborts the run, a failed employer check holds back that employer's postings, a Jev error leaves the posting pending, and a rejected keyless verdict leaves its employer's postings in the queue.
  • Least-privilege database login. Local .env files connect as jobfraud_local, which can read and write rows but cannot change the schema or truncate tables. Schema changes reach production only through a deploy.
  • An audit trail behind every researched verdict. EmployerWebSearchLog keeps the API judge's raw search blocks and, since 6 November 2026, the keyless helpers' reported queries and result URLs, append-only by convention. Presumed verdicts involve no search and write none.

The human loop

There is no public correction route, by design. The README says a rating is an automated screening signal that can be wrong. What exists is an owner-only queue on /audit/<token> pages, the app's only write path. The owner can add a ReviewNote, or file a JudgeRequest of one of two kinds. A rerun clears the posting's scoredAt at once, so the next judge pass re-scores it, and the API judge marks the request resolved when that happens. A deep request keeps the current score and queues the posting for a single-agent investigation with the owner's note passed in as context.

The posting stays on the site with its old score while the agent works. When the agent's verdict names the flagged posting, judge-keyless:apply re-scores it even though it is judged and stamps the request resolved. Before 6 November apply only scored pending postings, so a deep verdict updated the employer but never the posting the owner had flagged.

The update-postings skill runs a full refresh in this order:

  1. Drain the review queue: send each deep request to one fraud-analyst agent with the owner's note and apply its verdict, which re-scores the posting and stamps resolvedAt.
  2. Scrape twice, a term pass for software roles and a city-wide Victoria pass. Both are needed because they collect different postings.
  3. Pick the judge path from the ANTHROPIC_API_KEY predicate.
  4. Judge in waves, applying after every wave so an interrupted session loses nothing, until fetch reports zero pending.
  5. Report counts and cost. Data updates never need a deploy.

docs/self-improving-loop.md describes where this is meant to go: drift reports that file their own review requests, review decisions that become labels, and weight proposals measured against those labels in CI. Two steps stay human on purpose, labelling and merging rubric changes, because every merge changes published claims about named employers.

Known gaps

  • Ground truth is thin. There are 21 human labels and only 2 of them are High. The weights are unfitted, the baseline of 20 is deliberately unfitted, and the label test in CI catches large regressions but not small ones.
  • The address verdict is per employer. It describes one address, yet 61 employers mail to more than one, covering 519 postings. It belongs in a table keyed on the normalised address.
  • Nothing catches immigration brokers. Jev's brokerRouting answer looks promising on 8 postings and is stored on every composed row, but it carries no weight until a drawn sample of about 60 is labelled.
  • The Opus 5.5 impersonation check has never been compared side by side with its predecessor, and no labelled impersonation cases exist to measure it against.
  • Aggregator mislocations. A job in Houston, Texas listed as Houston, BC scores as a location mismatch instead of being recognised as out of scope.
  • 17,033 published ratings still come from the model-chosen era (see Where things stand today).
